# 元数据过滤：先把范围缩小，再算相似度

向量相似度分不清“话题对、但年份 / 部门 / 类型不对”的文档。问“2024 版的住宿标准”，2026 版手册里的同一节在语义上一样近。元数据过滤在召回之前按文档属性把候选圈小，范围外的块不参与任何一路召回。

依据的两篇文章：[《RAG 优化技术：元数据过滤》](https://mp.weixin.qq.com/s/71UrT5uwCSQtg4PhmoEpKw)、[《RAG 系统中的精准手术刀——元数据过滤》](https://mp.weixin.qq.com/s/B2dhhFN0kYsj1xXdvERD4g)。

## 1. 文章做法与本仓库的对应

| 文章里的做法 | 本仓库 | 说明 |
| --- | --- | --- |
| 给文档挂结构化标签（时间 / 领域 / 来源 / 权限） | 原有 | 标题、版本、生效与失效日期、部门、标签、密级；语料治理页可自动抽取并人工修正 |
| 前置过滤，而不是取 Top-K 再筛 | 原有，本次补齐 | 过滤结果是一组允许的块 ID，传给每一路召回。numpy、LanceDB 原本就是先筛后算；Qdrant、Chroma 原来是“取 4 倍再筛”，见第 4 节 |
| 权限与多租户隔离在检索层强制执行 | 原有 | 按顶栏“当前身份”的级别和部门过滤，不依赖模型拒答 |
| 时效：过期文档不召回 | 原有 | 按生效区间过滤；问历史规定时放行并标注失效 |
| 自查询：把自然语言翻译成过滤条件 | 本次新增 | 第 2 节 |
| 提前告诉模型有哪些字段和取值，防止臆造 | 本次新增 | 只给本库真实存在的取值，输出再校验一遍 |
| 空值处理：没填属性的文档别永远搜不到 | 本次新增 | `include_missing`，默认保留 |
| 时间字段可做范围查询 | 部分 | 年份按“标题 / 版本里的年份 + 生效区间覆盖的年份”计算；没有按任意日期区间过滤 |
| 按元数据预建分区索引 | 未做 | 单知识库规模下用不上；多租户已按知识库分目录 |

## 2. 自查询：从问题里读出条件

检索前，系统看一遍问题里有没有对“查哪些文档”的限定，支持四个属性：

| 属性 | 取值来源 | 例子 |
| --- | --- | --- |
| `year` 年份 | 标题、版本号里的年份；生效区间覆盖的年份（未写失效日期的算到今年）；`extra.year` | “2024 版的住宿标准” |
| `department` 部门 | 文档的发布 / 负责部门 | “基础架构部发布的手册里……” |
| `tags` 标签 | 文档的主题标签 | “售后方面的资料里，运费怎么算” |
| `file_format` 文件类型 | 文件扩展名 | “PDF 文档里……” |

三种方式，`retrieval.metadata_filter.mode`：

- `llm`（默认）：把本库现有的属性取值列给辅助模型，让它只在这些取值里挑条件。模型输出的字段和取值再对照一遍，库里没有的丢弃。没有文本模型或调用失败时退到 `rule`。
- `rule`：不调模型。只认问题里的独立年份，以及后面跟着“发布 / 制定 / 的制度 / 的文档”这类说法的部门名。标签和文件类型不识别。
- `off`：不识别。

识别出的条件是推测，所以有三道保险：

1. **条件不缩小范围就不生效。** 范围内的文档本来都满足时，什么也不做，也不提示。
2. **默认不排除没填该属性的文档**（`include_missing: true`）。标签通常填不全，排除会把没打标的文档整批丢掉。
3. **查不到就退回**（`fallback: true`）。条件匹配不到任何文档时不使用；按条件检索后没有任何结果时，去掉条件重查一次，并在链路说明里写明。

模型调用与查询变换并行。多跳和 Agentic 检索只在第一次识别，后续子查询沿用同一组条件。

识别结果写在检索链路里：检索实验室“查询层”卡片会显示条件、来源（模型 / 规则）和候选文档从几篇缩到几篇；对话的检索说明里也有同一条。

## 3. 手动指定条件

检索实验室输入框下方的“限定范围”可以直接选部门、标签、年份、文件类型，选项来自当前身份可见的现行文档。接口上是 `filters`：

```bash
curl -X POST localhost:8000/api/v1/retrieval/<kb_id>/playground \
  -H 'Content-Type: application/json' \
  -d '{"query":"年假规定","filters":{"year":[2026],"department":["人力资源部"]}}'
```

可选项用 `GET /api/v1/retrieval/<kb_id>/facets` 查。手动条件按字面执行：字段之间是“且”，同一字段的多个值是“或”，没填该属性的文档不算匹配。它和自动识别的条件叠加，自动条件只在手动条件圈定的范围内再缩小。

## 4. 向量库层面的预过滤

| 后端 | 过滤方式 |
| --- | --- |
| numpy | 先按掩码筛出允许的向量，再算相似度 |
| LanceDB | 允许的块不超过 5000 个时走 SQL 预过滤；更多时多取再筛，不够就加倍重取 |
| Qdrant | 允许的块不超过 5000 个时把条件下推（按 `chunk_id` 过滤后再找最近邻）；更多时多取再筛，不够就加倍重取 |
| Chroma | 多取再筛，不够就加倍重取，直到够数或取完全库 |

Qdrant 和 Chroma 原来固定取 `4 × top_n` 条再筛。允许的块如果都排在这之后，就会出现“库里有、却一条都搜不到”。现在改为下推或逐步加倍，测试里用“允许的 3 个块排在 60 个块的最后”验证过。

## 5. 实测

在“企业知识库（示例）”（6 篇文档）上，`bge-m3` + `bge-reranker-v2-m3`，条件识别用 `deepseek-flash`，关闭查询变换以单看过滤的影响：

- **普通问题不受影响。** 黄金集加合成集共 36 个没有范围限定的问题，`off` / `rule` / `llm` 三种方式的 Hit@1、Hit@5、MRR 都是 0.972，两种识别方式都没有在任何一个问题上产生条件。
- **带年份的问题不再新旧混杂。** “2024 版员工手册里出差住宿标准是多少”：`off` 时最终上下文里同时有 2024 版、2026 版和 FAQ；`rule` 排除了 2026 版；`llm` 同时识别出年份和“差旅”标签，只剩 2024 版。
- **库里没有的取值不会被编出来。** “2023 年关于云计算的进展”在这个库里不产生任何条件。
- **耗时。** 开着查询变换时，`llm` 方式的端到端中位耗时与 `off` 没有可见差别（约 2.0–2.4 秒，两轮各 10 个问题）；关掉查询变换后每次检索多约 0.6 秒。

提示词调过一次：最初的版本会把“M4 Pro 芯片的机型多少钱”里的产品词当成标签条件，规则方式会把“需要报人力资源部备案”当成部门限定。上面的数字是修正之后的。样本只有一个小库、几十个问题，换语料后要用自己的评测集再看。

## 6. 什么时候会帮倒忙

- **标签打得不全或太细。** 条件“标签=售后”会排除打了别的标签、但也讲售后的文档。示例库里的 FAQ 文档只有“增强语料”一个标签，任何标签条件都会把它排除。标签越准越有用；标签质量不好时把 `fields` 里的 `tags` 去掉，或改用 `rule`。
- **部门是“谁发布的”，不是“讲的是谁”。** “财务部的报销流程”多半在问流程本身，答案可能在人力资源部发布的手册里。提示词和规则都按这个口径写，但模型仍可能判断错。
- **主题单一的知识库。** 文档之间没有分类边界时，每个属性最多一种取值，系统会直接跳过识别。

## 7. 配置

```yaml
retrieval:
  metadata_filter:
    mode: llm                 # off | rule | llm
    fields: [department, tags, year, file_format]
    include_missing: true     # 识别出的条件不排除没填该属性的文档
    fallback: true            # 按条件查不到时去掉条件重查
```

“策略配置”页和检索实验室右侧的策略面板都能改。代码在 `prism/retrieval/metadata_filter.py`（取值目录、匹配、识别）和 `prism/retrieval/retriever.py`（接入召回前的过滤），测试在 `tests/test_metadata_filter.py`。
